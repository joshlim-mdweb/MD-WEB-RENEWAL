# checkout

세션 마감 루틴. /initiate의 반대. 프로젝트 파일을 갱신하고 실수 노트를 기록한다.

**왜 필요한가:** Claude는 세션이 끝나면 기억을 잃는다. 프로젝트 단위로 TODO와 컨텍스트를 저장해두면 다음 세션에서 어느 Claude든 바로 이어받을 수 있다.

---

## Step 0 — 프로젝트 확인

`docs/backlog/projects/` 디렉토리를 읽어 기존 프로젝트 파일 목록을 파악한다.

사용자에게 묻는다:

> "어떤 프로젝트로 저장할까요? (기존: {파일 목록} / 새 이름 입력 가능)"

- 기존 프로젝트 선택 시 → 해당 파일 업데이트
- 새 이름 입력 시 → `docs/backlog/projects/{name}.md` 신규 생성
- `docs/backlog/projects/` 디렉토리가 없으면 자동 생성

### 프로젝트 이름 규칙 (새 이름 입력 시 안내)

| 규칙 | 예시 |
|------|------|
| kebab-case, 영문 소문자 | `student-plan-renew` ✅ / `StudentPlan` ❌ |
| 기능·작업 영역 중심으로 — Jira Epic 이름과 맞출 것 | `checkout-flow`, `gnb-renewal` |
| 내부 툴·워크플로우 작업은 `claude-` prefix | `claude-workflow`, `claude-rules` |
| 너무 짧거나 모호한 이름 금지 | `test`, `work`, `temp` ❌ |
| 최대 30자 이내 | |

새 이름을 받으면 위 규칙 기준으로 문제가 있을 경우 한 줄로 지적하고 대안을 제시한다. 사용자가 그대로 쓰겠다고 하면 따른다.

---

## Step 1 — 프로젝트 파일 갱신

세션에서 다룬 내용을 정리해 프로젝트 파일을 **덮어쓴다** (append가 아닌 전체 갱신).

### 수집할 내용

1. 세션에서 나눈 대화 기반으로 완료된 항목·미결 항목 정리
2. 관련 Jira 티켓 목록 파악
3. 다음에 이어받을 사람이 바로 시작할 수 있는 컨텍스트 정리

### 저장 포맷

```markdown
---
project: {프로젝트 이름}
updated: {YYYY-MM-DD}
---

## 관련 Jira 티켓
- MDWEB-{id} — {제목} ({상태})

## TODO
1. {다음에 할 것 — 구체적 액션으로, 우선순위순}
2. {두 번째}
3. ...

## 컨텍스트
- {내린 결정과 이유}
- {미결 항목과 현재 상태}
- {블로커 또는 기다리는 것}

## 완료 로그
### {YYYY-MM-DD}
- {오늘 완료한 항목}
- {오늘 완료한 항목}
```

**완료 로그 규칙:**
- 기존 완료 로그는 유지하고 오늘 날짜 항목을 **맨 위에 추가**한다.
- TODO와 컨텍스트는 항상 최신 상태로 전체 교체한다.

---

## Step 2 — 실수 노트

사용자에게 묻지 않는다. **세션 대화를 직접 분석해** Claude가 자동으로 작성한다.

### 기록 대상

다음 중 하나라도 해당하면 기록한다:

- 사용자가 수정을 요구했거나 지적한 것 ("이건 아닌 것 같아", "아니 그게 아니라", "다시 해줘" 등)
- Claude가 잘못된 방향으로 진행하다 우회한 것 (파일 못 찾음, 툴 실패 후 재시도, 잘못된 가정 등)
- 같은 실수를 두 번 이상 반복한 것

해당 사항 없으면 Step 2 전체 스킵.

`docs/backlog/mistakes.md`가 없으면 헤더와 함께 새로 생성한다.

### 실수 노트 포맷 (append)

```markdown
## {YYYY-MM-DD}

**상황:** {어떤 작업 중에 발생했는지}
**실수:** {뭘 잘못했는지}
**원인:** {왜 그렇게 됐는지 — 짧게}
**다음엔:** {어떻게 피할지 — 구체적 행동}
```

여러 개면 같은 날짜 헤더 아래에 `---`로 구분해 이어 쓴다.

## Step 3 — 규칙 제안

Step 2의 실수 노트와 세션 전체를 근거로 **규칙 변경을 제안한다. 제안만 한다 — 파일을 고치지 않는다.**

실수를 기록만 하고 규칙에 반영하지 않으면 같은 실수가 반복된다. 이 Step이 그 환류 고리다.

### 제안 유형 4가지

| 유형 | 언제 |
|---|---|
| **추가** | 규칙에 없는 상황을 만나 Claude가 임의 판단했다. 같은 상황이 또 올 것이다 |
| **변경** | 규칙이 있는데 현실과 어긋난다. 지키면 오히려 틀린 결과가 나온다 |
| **개선** | 규칙이 맞지만 불명확해서 지켜지지 않았다. 문장을 다시 쓴다 |
| **제거** | 규칙이 다른 규칙과 충돌하거나, 죽은 참조이거나, 아무도 쓰지 않는다 |

### 판단 원칙

- **제거·통합을 먼저 검토한다.** 규칙 파일이 이미 많다 — 새 규칙을 얹는 게 항상 정답이 아니다. 실수의 원인이 "규칙이 없어서"가 아니라 "규칙이 너무 많아 안 읽혀서"일 수 있다
- **같은 실수 3회 이상이면 금지 패턴으로 승격**을 제안한다 (`mistakes.md`에서 과거 이력 확인)
- 규칙이 안 지켜진 이유를 먼저 본다 — 불명확이면 **개선**, 과다면 **제거**, 진짜 공백이면 **추가**
- 대상 파일과 섹션을 **정확히 지목한다.** "어딘가 고치면 좋겠다" 식 제안 금지
- 세션에서 실제로 문제가 된 것만 제안한다. 일반론·예방적 제안 금지

### 출력 포맷

```markdown
## 규칙 제안 {N}건

### 1. [추가|변경|개선|제거] {대상 파일} §{섹션}
- **근거**: {이 세션에서 실제로 무슨 일이 있었는지 — 실수 노트 항목과 연결}
- **현재**: {지금 규칙이 어떻게 돼 있는지 / 없으면 "규칙 없음"}
- **제안**: {구체적으로 어떻게 바꿀지 — 문장까지}
- **영향**: {이걸 바꾸면 다른 규칙·커맨드에 영향이 있는지}
```

제안할 게 없으면 `## 규칙 제안 — 없음` 한 줄로 끝낸다. **억지로 만들지 않는다.**

### 적용

Josh가 승인한 항목만 적용한다. 승인 없이 규칙 파일을 수정하지 않는다.
승인받아 적용했으면 Step 1의 프로젝트 파일 완료 로그에 반영한다.

## 규칙

- Step 0은 **매핑이 자명하면 묻지 않는다** — 세션에서 다룬 주제가 기존 프로젝트 파일과 명확히 맞으면 바로 그 파일로 저장하고 결과만 보고한다. 애매하거나 여러 프로젝트에 걸칠 때만 묻는다
- Step 1은 항상 실행 (사용자 입력 없이 자동 저장)
- Step 2는 Claude가 세션 대화를 분석해 자동 작성 — 사용자에게 묻지 않는다
- Step 3은 **제안까지만.** 승인 없이 규칙 파일을 고치지 않는다
- 저장 후 파일 경로를 출력한다 (사용자가 확인할 수 있도록)

# /copy-review — 문구 검수 Skill

`.claude/rules/ux-writing.md` 기준으로 사용자 노출 문구를 검수한다.
**출력 전에 돌린다.** Josh에게 보여준 뒤 지적받는 것이 아니라, 보여주기 전에 스스로 잡는 것이 목적이다.

---

## 자동 실행 조건 (필수)

아래 상황에서는 요청이 없어도 **반드시** 이 검수를 거친 뒤 출력한다.

| 상황 | 검수 대상 |
|---|---|
| Figma 와이어프레임 작성·수정 | WF 내 모든 UI 문구 + Description·Annotation |
| Josh와 문구 작업 (버튼·에러·토스트·빈 상태·배너) | 작성한 문구 전체 |
| FAQ · 정책 안내 · 약관 본문 작성 | 본문 + 그 안의 버튼·링크 |
| 마케팅 카피 (Hero · Feature · Solutions) | 헤드라인 + 서브카피 |
| PRD·정책 문서 안의 **UI 노출 문구 인용** | 인용된 문구만 (문서 본문은 `policy-writing.md` 소관) |

검수 결과가 전부 통과면 결과를 따로 보고하지 않고 문구만 출력한다.
**위반이 있으면 고친 뒤, 무엇을 왜 고쳤는지 짧게 남긴다.**

---

## 검수 절차

### Step 1 — 텍스트 종류 판별

문구마다 종류를 먼저 정한다. 여기가 틀리면 나머지가 전부 틀린다.

```
마케팅 카피 (Hero·Feature·Solutions)      → 명사형 종결
사이트 본문 (FAQ·정책 안내·약관)          → 합니다체
제품 UI 문구 (토스트·에러·빈 상태·배너)   → 합니다체
버튼·레이블·플레이스홀더                  → 명사형
```

한 화면에 여러 종류가 섞이는 것은 정상이다. **한 문장 안에 두 격이 섞이면 위반이다.**

### Step 2 — 기계적 위반 검출

문자열 매칭으로 잡히는 것부터 전수 확인한다.

**EN (원본이므로 먼저 본다)**

| 검출 | 조치 |
|---|---|
| 버튼·제목이 Title Case 아님 | Title Case로 |
| 본문·에러가 Title Case임 | Sentence case로 |
| 제품 용어 소문자 (`seat` · `organization` · `sw account`) | 대문자로 (`Seat` · `Organization` · `SW Account`) |
| 버튼·플레이스홀더 끝 마침표 | 제거 |
| 본문·에러·토스트 끝 마침표 없음 | 추가 |
| 느낌표 | 제거 |
| 나열에 Oxford comma 없음 | 추가 |
| 날짜가 `01/02/2026` 형식 | `January 1, 2026` |
| 미래 시제 `will be` 남발 | 현재 시제로 |
| 명사 3개 연속 · 단독 `it`/`this`/`that` | 대상을 이름으로 다시 씀 |
| 20단어 초과 문장 | 자름 |

**KO**

| 검출 | 조치 |
|---|---|
| `~해요` · `~돼요` · `~예요` · `~됐어요` | 합니다체로 교체 |
| `~하세요` · `~하십시오` (명령조) | `~해 주세요` |
| `~하시기 바랍니다` | `~해 주세요` |
| 버튼에 `하기` (`저장하기`·`결제하기`) | `하기` 제거 — 단, 순우리말(`닫기`·`건너뛰기`)은 유지 |
| 버튼 `확인` · `Confirm` · `OK` 단독 | 액션 에코로 교체 |
| 다이얼로그 왼쪽 버튼이 `취소` | `닫기` |
| `죄송합니다` · `감사합니다` · `!` | 삭제하고 결과·해결책으로 |
| `성공적으로` · `Successfully` | 삭제 |
| `Kindly` · `Simply` · `Just` · `Click here` | 삭제 또는 구체적 동사 |
| EN 버튼이 Title Case 아님 | Title Case로 |
| 폐지 용어 `Group` · `Copy` · `License ID` · `MemberType` | `policy-writing.md` §5 기준 신 용어 |

### Step 3 — 판단이 필요한 항목

기계로 안 잡히는 것. 문구마다 물어본다.

**용어 (P2)**
- 도메인 용어(패턴·시뮬레이션·리깅·Alembic)를 굳이 풀어 설명하고 있지 않은가?
- 제품 용어(Seat·Organization·SW Account·Student Benefit)를 설명 없이 던지고 있지 않은가?
  - 이 화면이 그 용어의 **첫 등장**이면 한 줄 설명이 있어야 한다
  - 이미 설명한 화면이면 반복하지 않는다

**구조**
- 결과가 첫 문장에 있는가? (P1)
- 되돌릴 수 없는 동작에 **영향 범위**가 있는가? (P3) — 라이선스·구독·Seat는 팀 전체에 영향
- 빼도 뜻이 같은 단어가 남아 있지 않은가? (P4) — `혹시`·`해당`·`정말`·`바로`·`손쉽게`
- 제목이 말한 것을 본문이 다시 말하고 있지 않은가? (P4)

**번역·정책**
- 관용구·말장난이 있어 4개 언어 번역에서 무너지지 않는가? (P5)
- 제약을 결정 **전에** 알려주는가? (P6) — Student 4년 제한 같은 것을 구매 후에 안내하지 않는가
- 불안을 만들어 구매를 유도하지 않는가? (P6)

**리듬**
- 같은 종결어미가 세 문장 이상 연달아 반복되지 않는가?

### Step 4 — 사실 검증

문구가 주장하는 정책이 실제 정책과 맞는지 확인한다. **말투만 보고 끝내지 않는다.**

근거는 `docs/policy/**`와 3개 Slack Canvas다.

```
Plan Renew        F0BCBS8G88N
Order·Checkout    F0BL0SRE4TZ
Account Structure F0BBYNQ3S8P
```

가격·인증 조건·기간 제한·결제 수단을 문구에 쓴 경우 해당 정책 파일을 열어 대조한다.
근거를 못 찾으면 문구를 지어내지 말고 `*(정책 확인 필요)*` 플래그를 단다.

## 출력 형식

### 전부 통과

문구만 출력한다. 검수했다는 말을 따로 하지 않는다.

### 위반 있음

고친 문구를 먼저 내고, 아래에 짧게 덧붙인다.

```markdown
**수정 3건**
- 버튼 `저장하기` → `저장` (§4.2 `하기` 제거)
- 토스트 `저장됐어요` → `저장했습니다` (§1 해요체 금지)
- `SW Account를 선택해 주세요` → 첫 등장이라 한 줄 설명 추가 (P2)
```

한 줄 = 수정 1건. 근거 절 번호를 붙인다. 장황한 설명을 쓰지 않는다.

### 판단 보류

정책 근거가 없거나 Josh 결정이 필요하면 고치지 말고 표시한다.

```markdown
**확인 필요 1건**
- ⑦ 커뮤니티 문의처 — 정확한 명칭·진입 경로가 정책 문서에 없음
```

---

## 하지 않는 것

- 통과한 항목을 나열하지 않는다. 위반만 보고한다.
- 문서 본문(PRD·정책서) 말투를 이 기준으로 고치지 않는다 — `policy-writing.md` 소관이다
- 정책 근거 없이 문구를 지어내지 않는다
- 검수를 이유로 확정된 문구(마케팅 카피 레퍼런스 예시 등)를 바꾸지 않는다

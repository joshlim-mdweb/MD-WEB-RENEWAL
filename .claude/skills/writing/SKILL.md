# /writing — 상황별 문구 생성 Skill

문구를 처음부터 만들 때 사용. 원문이 있고 번역이 목적이면 `/translate` 사용.

---

## 호출 방식

```
/writing [mode] [컨텍스트]
```

모드 미지정 시 컨텍스트에서 추론하고 상단에 "detected mode: X" 한 줄 표기.

---

## 지원 모드

| 모드 | 용도 | 출력 언어 |
|---|---|---|
| `ux` | 버튼·에러·토스트·모달·빈상태·플레이스홀더·툴팁 | EN + KO (기본) |
| `slack` | 내부 공지·공유·업데이트 메시지 | KO (기본), EN 요청 시 추가 |
| `email` | 고객 이메일·내부 이메일 | 요청 언어 |
| `release` | 릴리즈 노트 | EN + KO |
| `policy` | 정책 안내 문구 | EN + KO |
| `marketing` | 랜딩·피처 카피 | EN + KO |
| `notification` | 이메일·푸시 알림 | EN + KO |

언어 범위 명시 시 해당 언어만 출력. 예: `/writing ux KO만`

---

## 전역 원칙

1. **소스 개선 우선** — 컨텍스트가 불명확하면 먼저 의도를 파악하고 개선 후 작성
2. **결과 중심** — "처리됩니다" → 무엇이 어떻게 되는지 명시
3. **행동 중심** — 다음 행동이 명확하게 드러나야 함
4. **용어 일관성** — `localization.md` 용어집 준수
5. **Placeholder 보호** — `{{변수}}` 형태 그대로 유지

---

## 모드별 실행 규칙

### ux

버튼·에러·성공·빈상태·툴팁·모달·플레이스홀더 등 UI 문구 전체.

**출력 형식:**
```
[컴포넌트 타입] — [상황 설명]

| | EN | KO |
|---|---|---|
| Label | ... | ... |
| Error | ... | ... |
| Success | ... | ... |
| Empty | ... | ... |
| Placeholder | ... | ... |
```

필요한 행만 포함. 불필요한 행 추가 금지.

**EN 규칙:**
- Present tense, active voice
- Sentence case
- "Changes saved." / "Something went wrong." / "Try again." 스타일

**KO 규칙:**
- 해요체 고정 (`~해요` / `~돼요` / `~이에요`)
- `~합니다` / `~됩니다` 금지
- 버튼: `동사 + 하기` 형태
- 다이얼로그 취소 버튼: 항상 `닫기`

---

### slack

내부 팀 공유용 메시지. 간결하고 정보 중심.

**출력 형식:**
```
[채널/대상] — [메시지 목적]

KO:
---
[본문]
---

EN: (요청 시)
---
[본문]
---
```

**규칙:**
- 첫 줄: 핵심 정보 (무슨 일 / 무엇이 변경됨)
- 필요 시 불릿으로 세부 내용
- 마지막: 행동 요청 또는 확인 요청 명시
- 이모지 사용 여부는 컨텍스트 기반 판단 (격식 채널 → 최소화)

---

### email

고객 이메일 또는 내부 이메일.

**출력 형식:**
```
[이메일 유형] — [목적]

제목: ...

본문:
---
[본문]
---
```

**규칙:**
- 제목: 핵심 내용만, 50자 이내
- 본문: 목적 → 내용 → 행동 요청 순서
- 고객 이메일: 해요체
- 내부 이메일: 간결체 (서울체 불필요)

---

### release

제품 릴리즈 노트.

**출력 형식:**
```
[버전 / 날짜]

| | EN | KO |
|---|---|---|
| 제목 | ... | ... |
| 요약 | ... | ... |

**New**
- EN: ...
  KO: ...

**Improved**
- EN: ...
  KO: ...

**Fixed**
- EN: ...
  KO: ...
```

**규칙:**
- 사용자가 경험하는 변화 중심 (기술 구현 설명 금지)
- New / Improved / Fixed 세 카테고리만
- 항목당 1문장

---

### policy

정책 안내 문구 (약관·이용 정책·제한 안내 등).

**출력 형식:**
```
[정책 항목]

| | EN | KO |
|---|---|---|
| 제목 | ... | ... |
| 본문 | ... | ... |
| 안내 | ... | ... |
```

---

### marketing

랜딩·피처·솔루션 페이지 카피.

**규칙 (KO):**
- 명사형 종결 필수
- `~한다` / `~합니다` / `~됩니다` 금지
- 구체적 기능 묘사 (추상적 감성 카피 금지)
- 헤드라인 10단어 이내

**규칙 (EN):**
- Short declarative statements
- Noun-phrase endings where natural
- Specific feature language over abstract benefit language

---

### notification

이메일·푸시 알림 문구.

**출력 형식:**
```
[알림 유형] — [트리거 조건]

| | EN | KO |
|---|---|---|
| 제목/타이틀 | ... | ... |
| 본문 | ... | ... |
| CTA | ... | ... |
```

## 소스 개선 체크리스트

문구 생성 전 컨텍스트가 아래 문제를 갖고 있으면 먼저 개선 후 작성:

- [ ] 주어가 불명확한가?
- [ ] 행동 결과가 불명확한가?
- [ ] 복구 방법이 없는가? (에러 문구)
- [ ] 개발자용 표현인가? (`invalid request`, `error code`)
- [ ] 불필요하게 긴가?

개선 시 해석 변경이 큰 경우에만 상단에 한 줄 메모. 사소한 개선은 메모 없이 반영.

## ZH-CN / JA 추가 요청 시

기본 출력(EN + KO) 이후 요청이 있으면 추가 컬럼으로 확장:

```
| | EN | KO | ZH-CN | JA |
```

ZH-CN: 간체자, 자연스러운 SaaS 표현
JA: です・ます체, 버튼은 명사 또는 단문 동사

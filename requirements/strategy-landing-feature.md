## 배경

MD 웹사이트 리뉴얼의 Features 페이지 전략 문서. 제품 기능을 어떻게 구조화하고, 어떤 언어로 전달하며, 솔루션 페이지들과 어떻게 연결할지 정의한다.

---

## 1. 페이지 목적

**Features 페이지는 "MD로 무엇을 할 수 있는가"를 답하는 페이지다.**

솔루션 페이지(Individual / Enterprise / Student / Academic)가 "나에게 왜 필요한가"를 답하는 것과 역할이 다르다. 기능 탐색 단계의 사용자 — 이미 MD를 알고 구체적으로 무엇이 가능한지 확인하러 온 사람들을 위한 페이지.

| | Features | Solutions |
|--|---------|---------|
| 질문 | MD로 무엇을 할 수 있나? | 나에게 왜 필요한가? |
| 내용 | 기능 설명 (how it works) | 페르소나 가치 (what I get) |
| 타겟 | 기능 탐색 단계 | 의사결정 단계 |
| 링크 방향 | → Solutions (페르소나 연결) | → Features (기능 심화) |

## 2. 페이지 타이틀 & 히어로

| 요소 | 확정 카피 |
|------|---------|
| **페이지 타이틀** | `Creation powered by simulation.` |
| **서브타이틀** | `Define the pattern, set the fabric, and watch your clothes move like the real thing.` |
| **CTA 1** | `View Plan` |
| **CTA 2** | `Start with 2 weeks Trial` |

**전략 근거:** "Creation powered by simulation"은 MD의 핵심 기술 차별점을 한 줄로 압축한다. 다른 3D 툴의 폴리곤 기반 모델링 vs. MD의 물리 시뮬레이션 — 이 차이가 모든 기능의 공통 기반이다.

---

## 3. 섹션 구조 & 카피 확정안

총 5개 섹션. 각 섹션 = 섹션 타이틀 + 헤드라인 + 디스크립션 + 이미지 2장.

### 섹션 1 — MODELLING

| 요소 | 카피 |
|------|------|
| 섹션 타이틀 | `Modelling` |
| 헤드라인 | `폴리곤이 아닌, 패턴으로.` |
| 디스크립션 | `실제 봉제 패턴을 배치하고, 봉제선으로 연결. 현실의 재단 방식을 그대로 옮긴 워크플로우.` |
| 이미지 1 | 2D 패턴 에디터 화면 (패턴 + 봉제선) |
| 이미지 2 | 3D 결과물 미리보기 |

**전략 포인트:** MD의 가장 근본적인 차별점. "폴리곤이 아닌"은 경쟁 툴(Maya, Blender 등)과 직접 대비. 기술 설명이 아닌 방식의 차이로 표현.

---

### 섹션 2 — TEXTURE & FABRIC

| 요소 | 카피 |
|------|------|
| 섹션 타이틀 | `Texture & Fabric` |
| 헤드라인 | `실크는 흘러내리고, 데님은 버틴다.` |
| 디스크립션 | `소재별 무게, 탄성, 마찰 계수 설정으로 각 소재 고유의 텍스쳐와 움직임 구현. 천의 성질, 중력, 마찰까지 의도한 대로.` |
| 이미지 1 | 소재별 시뮬레이션 비교 (실크 vs 데님) |
| 이미지 2 | Material 속성 패널 UI |

**전략 포인트:** 단순한 텍스쳐 매핑이 아닌 물성 시뮬레이션. 실크/데님 대비로 즉시 체감되는 차이를 전달. 게임·VFX·패션 모든 도메인에 적용되는 공통 가치.

---

### 섹션 3 — RIGGING

| 요소 | 카피 |
|------|------|
| 섹션 타이틀 | `Rigging` |
| 헤드라인 | `어떤 캐릭터에도, 자동으로.` |
| 디스크립션 | `체형도 포즈도 가리지 않고, 어떤 캐릭터든 골격에 맞게 자동 피팅.` |
| 이미지 1 | 다양한 캐릭터 체형에 의상 피팅된 비교 화면 |
| 이미지 2 | 포즈 변경 시 의상 반응 |

**전략 포인트:** 스튜디오·프리랜서가 이미 보유한 캐릭터 에셋 재활용 가능. "어떤 캐릭터에도"는 범용성과 파이프라인 호환성을 동시에 전달.

---

### 섹션 4 — ANIMATION

| 요소 | 카피 |
|------|------|
| 섹션 타이틀 | `Animation` |
| 헤드라인 | `모든 프레임, 물리적으로 정확하게.` |
| 디스크립션 | `캐릭터의 움직임에 맞게 천의 물리 반응을 매 프레임 계산, 시뮬레이션 캐시로 저장. 자연스러운 주름과 흐름이 자동으로.` |
| 이미지 1 | 캐릭터 동작 중 의상 시뮬레이션 스틸컷 |
| 이미지 2 | 타임라인 / 캐시 저장 UI |

**전략 포인트:** "주름을 손으로 키프레임하지 않아도 된다"는 임팩트. VFX·게임 애니메이터에게 가장 직접적인 시간 절감 포인트. 시뮬레이션 캐시 언급으로 파이프라인 통합 가능성 암시.

---

### 섹션 5 — RENDERING

| 요소 | 카피 |
|------|------|
| 섹션 타이틀 | `Rendering` |
| 헤드라인 | `파이프라인은 그대로.` |
| 디스크립션 | `FBX, Alembic, OBJ 포맷으로 내보내 Maya, Houdini, Unreal Engine, Unity와 직접 연동. 기존 파이프라인 변경 없이.` |
| 이미지 1 | MD → 렌더러 파이프라인 다이어그램 또는 UE 렌더 결과 |
| 이미지 2 | 포맷 내보내기 UI |

**전략 포인트:** MD는 최종 렌더러가 아님을 인정하면서, 오히려 "기존 툴을 그대로 쓸 수 있다"는 안도감으로 전환. 파이프라인 진입 장벽 제거가 핵심 메시지.

## 5. Solutions 페이지 연결 전략

Features 섹션마다 Solutions 링크 sub-tag 2개 포함 예정.

```
[Block N]
헤드라인 + 디스크립션 + 이미지
└── [개인 디자이너에게 →]   /solutions/individual
└── [엔터프라이즈에게 →]    /solutions/enterprise
```

각 sub-tag는 해당 기능이 그 페르소나에게 주는 가치를 한 줄로 → Solutions 페이지에서 심화.
